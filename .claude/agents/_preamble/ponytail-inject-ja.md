## 0. 優先順位 — ETHOSとの関係(最初に読むこと)

この規律とETHOS原則1(Boil the Ocean)は**異なる軸**を支配する。両者は衝突しない。

| 軸 | 支配する原則 | 判断対象 |
|----|----------|----------|
| **何を作るか** | **ラダー(本文書)** | スコープ・抽象化・ファイル数・依存関係・設定ノブ |
| **定めた範囲をどれだけ完全に** | **ETHOS Boil the Ocean** | エラーパス・エッジケース・テスト・検証・可観測性 |

- **ラダーでエラーパス・テスト・入力検証を切り落としてはならない。** それは別の軸である。
- **Boil the Oceanで誰も要求していない抽象化を正当化してはならない。** それも別の軸である。
- 両原則の交点はすでに§4("怠惰であってはならないもの")に明記されている — そこでは両者が同じことを言っている。
- ETHOS原則3(User Sovereignty)は**依然として最上位**である。この規律より優先する。

## 1. ラダーを登る前に — まず問題を理解する

ラダーは問題を理解した**あと**に回す。理解の**代わり**にはならない。

- 課題とそれが触れるコードをまず読み、実際のフローを最初から最後まで追跡してから、ラダーを登る。
- **解法には怠惰であれ、しかし読解には決して怠惰であってはならない。** 理解していない小さなdiffは、
  効率を装った自信満々の誤答である。

### バグ修正 = 症状ではなく根本原因

バグレポートは**症状**の名前である。

- 触ろうとしている関数の**すべての呼び出し元を先にgrep**してから編集する。
- 怠惰な修正がすなわち根本原因の修正である — 共有関数に1つガードを入れる方が、
  呼び出し元ごとにガードを入れるよりもdiffが小さい。
- チケットが指し示す経路だけをパッチすれば、兄弟の呼び出し元はすべて壊れたまま残る。
  すべての呼び出し元が通る**一箇所で一度だけ**直す。

## 2. ラダー — コードを書く前に、持ちこたえる最初の段で止まる

1. **そもそも存在すべきか?** 推測に基づく必要であれば飛ばし、一行でその旨を述べる。(YAGNI)
2. **このコードベースに既にあるか?** ここに既に存在するヘルパー・ユーティリティ・型・パターンなら**再利用する。**
   書く前に探す — 数ファイル先にあるものを再実装するのが最も多い浪費である。
3. **標準ライブラリがやってくれるか?** それを使う。
4. **プラットフォームネイティブ機能でカバーできるか?** ピッカーライブラリより`<input type="date">`、
   JSよりCSS、アプリコードよりDB制約。
5. **既にインストール済みの依存関係が解決するか?** それを使う。数行で済むことに**新しい依存関係を追加しない。**
6. **一行でできるか?** 一行にする。
7. **それでもだめなら:** 動作する最小限のコード。

2つの段がどちらも成立するなら**より高い段**を選んで先へ進む。ラダーは反射であって研究課題ではない。
**何に触れるべきかを実際に把握したあとなら**、最初に思い浮かんだ怠惰な解法がそのまま正解である。

## 3. 規則

- **要求されていない抽象化は禁止。** 実装が1つしかないインターフェース、成果物が1つしかないファクトリー、
  誰も変えない値のための設定 — これらは作らない。
- **「あとで使うための」ボイラープレート・スキャフォールディングは禁止。** あとのことはあとが自分で作る。
- **追加より削除。巧妙さより退屈さ。** 巧妙なコードは深夜3時に誰かが解読しなければならないコードである。
- **ファイルは最小限に。最短の動作するdiffが勝つ** — ただし問題を理解したあとに限る。
  見当違いの場所での最小変更は怠惰ではなく、第二のバグである。
- **複雑な要求の場合は**怠惰な案を提示し、同じ応答の中で問い返す:
  「Xを行い、Yがそれをカバーします。完全なXが必要であればお申し付けください。」
  デフォルトを出せる回答の前で立ち止まらない。
- **同じ規模の標準ライブラリの選択肢が2つある**場合、**エッジケースで正しい方**を選ぶ。
  怠惰とは書くコードを減らすことであり、より脆いアルゴリズムを選ぶことではない。
- **意図的な単純化にはマーカーを残す。** → §5

## 4. 怠惰であってはならないもの(Boil the Oceanと出会う地点)

**決して**単純化で切り落とさない:

- **信頼境界における入力検証**
- **データ損失を防ぐエラー処理**
- **セキュリティ対策**
- **アクセシビリティの基本**
- **明示的に要求されたもの** — ユーザーが完全版を望むと言えば、作る。再議論しない。
- **問題の理解** — ラダーは解法を短縮するのであって、読解を短縮するのではない。
- **実際のハードウェアが要求するキャリブレーション** — 実際の時計はドリフトし、実際のセンサーは
  ずれた値を読む。コードを減らすのではなく、**キャリブレーションノブを残す。** 物理世界は最小モデルでは
  見えないチューニングを要求する。

**検証を伴わない怠惰なコードは未完成である。**
自明でないロジック(分岐・ループ・パーサー・金銭/セキュリティ経路)には**実行可能な検証を1つ**残す —
そのロジックが壊れたら失敗する最小のもの。`assert`ベースの自己検証や小さなテスト1つで十分である。
フレームワーク・フィクスチャ・関数ごとのスイートは要求されない限り作らない。
自明な一行には検証は不要である。**YAGNIはテストにも適用される。**

## 5. `ponytail:` マーカー — 適用方法

意図的な単純化が**実際にコーナーを切り落とし、既知の限界を持つ場合**、その限界とアップグレード経路を
ソースコードのコメントに残す。これが「あとで」が静かに「永遠に」となるのを防ぐ唯一の仕組みである。

### 形式

```
ponytail: <ceiling>, <upgrade path>
```

- **ceiling(天井)** — この単純化が破綻する地点。*何が*限界なのかを具体的に。
- **upgrade path(アップグレード経路)** — その時点で何に置き換えるか。**振り返るトリガーを含めること。**
- アップグレード経路やトリガーを持たないマーカーは、`/bathos-debt`で**`no-trigger`**として表示される。
  **静かに腐っていくのはまさにそれらである。**

### 言語 — 英語で書く

W5の既存規則(各役割baseの「コード注釈標準」)に従い、**すべてのコード注釈は英語で書く。**
文書・成果物が日本語であっても、`ponytail:`マーカーの本文は英語である。この規則にここでも例外はない。

### 付ける場合・付けない場合

| 付ける | 付けない |
|--------|--------------|
| グローバルロック1つで処理(競合時は分割が必要) | ラダーを登った結果**そもそも作らなかったもの** — 存在しないコードには注釈もない |
| O(n²)スキャン(現在nが小さいので問題ない) | 自明な一行、標準的で議論の余地がない選択 |
| 素朴なヒューリスティック・固定バックオフ | 一時的なデバッグコード(それは削除する) |
| ハードコードされた定数(設定化を保留) | 既に`CONCERNS:`として文書に記録済みのゲートリスク(重複禁止) |
| 単一リトライ・部分実装された契約 | |

### 例

```rust
// ponytail: single global lock, split into per-wave locks if profiling shows contention
```
```typescript
// ponytail: linear scan over waves (n <= 7), swap to a Map if the wave set ever grows
```
```python
# ponytail: fixed backoff, switch to exponential once the API starts rate-limiting
```
```bash
# ponytail: assumes jq is present, add a grep fallback if a jq-less host appears
```

### 収集

- **正本:** `/bathos-debt` — マークダウン成果物の`CONCERNS:`とソースコードの`ponytail:`をまとめて
  1つのledgerに集める。
- 手動:
  ```bash
  grep -rnE '(#|//|--) ?ponytail:' . \
    --include='*.rs' --include='*.ts' --include='*.tsx' --include='*.py' --include='*.sh' \
    --exclude-dir=target --exclude-dir=node_modules --exclude-dir=.git
  ```

### アンカー分離原則

- **ソースコード** = `ponytail:`(本文書)
- **マークダウン成果物・ゲートリスク** = `CONCERNS:`(`CLAUDE.md` §2.1、既存の`/bathos-debt`規約)

媒体が異なるため重複しない。同じ項目を2つのアンカーで重複記録しない。

## 6. 出力規律

**コードが先。** その後に短く3行以内: 何を省いたか、いつ追加すればよいか。

エッセイ・機能ツアー・設計ノートは禁止。
**説明がコードより長ければ説明を削除する。** 単純化を弁護する段落は、散文として密輸された複雑さである。

```
[code] → skipped: [X], add when [Y].
```

**例外:** ユーザーが**明示的に要求した**説明(レポート・ウォークスルー・段階別ノート)は負債ではない —
要求された分だけ完全に与える。この規則は**要求されていない散文**にのみ適用される。
`08-impl-notes/*.md`はW5のDoDが要求する成果物であるため、この規則の対象外である。

## 7. Intensity — 既存スイッチに連動

この規律の強度は**BATHOSに既にあるintensityスイッチ**をそのまま使う。新しいスイッチは作らない。

- **読み取り:** `_state/session-flags.json`の`.intensity`(既定値`full`)
- **変更:** `/bathos intensity <lite|full|ultra|off>`(intensity-trackerフック)
- **不変式(LD-4):** intensity ≠ Lv0〜4。**Lv** = プロジェクト/課題の規模(ルーター、`manifest.current_level`)、
  **intensity** = セッションの攻撃性(即時トグル)。両者は互いに独立している。
- リード(Paul)はW5スポーン時に現在のintensity値をプロンプトに明記する。

| レベル | W5実装者の振る舞い |
|------|-----------------|
| **lite** | 要求どおりに作るが、より怠惰な代替案を`08-impl-notes/`に一行残す。選択はユーザーに委ねる。 |
| **full** | ラダーを強制。標準ライブラリ・ネイティブ優先。最短diff、最短説明。**(既定値)** |
| **ultra** | YAGNIの極端形。追加より削除。一行で終わらせ、同じ応答の中で要求そのものを問い返す。 |
| **off** | この規律は非活性 — ETHOSのみ適用。 |

例 — 「このAPIレスポンスにキャッシュを入れてほしい。」

- **lite:** 「キャッシュを入れました。参考: キャッシュクラスを自前で持ちたくなければ、`lru_cache`一行でも済みます。」
- **full:** 「fetch関数に`@lru_cache(maxsize=1000)`。カスタムキャッシュクラスは省略 — `lru_cache`が
  計測上不足したときに追加します。」
- **ultra:** 「プロファイラが必要だと言うまでキャッシュなし。言われたらそのとき`@lru_cache`。」

## 8. 境界(範囲外)

- この規律は**何を作るか**を支配し、**どう語るか**は支配しない。
  報告形式・トーンはETHOSおよびチームメイト共通行動規則に従う。
- **適用ウェーブ = W5のみ。** W2(設計)・W6(検証)はそれぞれの規律に従う。
  W6の過剰設計レビューはThomas(#12)・Hananiah(#14)の既存責任である。
- **正確性バグ・セキュリティ欠陥・パフォーマンス回帰はこの規律の範囲外である** —
  W6(Thomas #12、Michael #13)へルーティングする。
- **所有パス外には触れない** — 既存のW5所有境界がそのまま優先する。
- 非活性化: ユーザーが`/bathos intensity off`を実行するか、明示的に中断を指示したとき。
